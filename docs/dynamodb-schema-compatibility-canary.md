# stable/canary共存中のDynamoDBスキーマ互換性ガイドライン

ブルーグリーンデプロイ導入（issue #1319）により、`stable`・`canary`の2つのバックエンドコードが、最長1週間（Task 12の自動昇格サイクル）同一のDynamoDBテーブル（`backend/serverless-data.yml`で定義、issue #1320参照）を共有する。この間、新旧コードが同時に同じテーブルを読み書きしても壊れないよう、スキーマ変更には以下の開発規律（expand/contract方式）を適用する。

## チェックリスト

PRでDynamoDBテーブルのスキーマ（属性・GSI）を変更する場合、以下を確認する。

- [ ] **属性の追加か**: 常に安全。追加する属性は省略可能な形にし、まだ書いていない旧コードが読んだ際に欠落していても正常に動作することを確認する
- [ ] **属性の削除・リネームか**: 1リリースで行わない。以下の最低2サイクルに分ける
  1. **サイクル1（追加）**: 新しい属性名を追加し、新コードは新旧両方の属性を読めるようにする（書き込みは新属性のみでよい）
  2. **昇格を待つ**: Task 12の自動昇格（または管理者判断）により、新コードが`stable`へ完全昇格し、旧コードが稼働するインスタンスが存在しなくなったことを確認する
  3. **サイクル2（削除）**: 旧属性を読むコードが存在しないことを確認したうえで、旧属性を削除する
- [ ] **GSIの追加か**: 安全。既存のクエリパターンに影響しない
- [ ] **GSIの削除か**: 新旧どちらのコードもそのGSIを参照しなくなってから行う。属性の削除・リネームと同様、2サイクルに分ける
- [ ] 本ドキュメントの「スコープ外とする変更」に該当しないか確認する（該当する場合は後述の対応に従う）

## 具体例（karutaの既存テーブル）

`backend/serverless-data.yml`で定義されているテーブルを例に、各パターンへの当てはめ方を示す。

- `karuta-phrases`（パーティションキー`category`、ソートキー`id`）へ新しい表示用属性を追加する場合: 属性追加（安全）に該当する
- `karuta-quiz-room-connections`のGSI（`roomId`）を別のキーへ差し替える場合: GSIの削除＋追加に該当するため、新GSIを先に追加し、旧GSIへの参照が無くなったことを確認してから旧GSIを削除する2サイクル構成にする

## スコープ外とする変更（既知の限界）

expand/contract方式（2サイクルに分ける）でも後方互換を保てない変更は、本ガイドラインの対象外とする。

- パーティションキー・ソートキーの変更
- 属性の型を破壊的に変える移行（例: 文字列→数値で既存データの変換が必要な場合）

このような変更が必要になった場合、カナリア方式（1週間の`stable`/`canary`共存）をそのまま使うことはできない。明示的なメンテナンスウィンドウ（`canary`を一時停止し`stable`のみでデータ移行する等）のようなアドホックな対応が必要になる。具体的な対応方法は本ドキュメントのスコープ外とし、実際に必要になった時点で別issueとして起票しバックログ化する。
